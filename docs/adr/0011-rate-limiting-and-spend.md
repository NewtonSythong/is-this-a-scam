# A per-caller cap in memory, and the real limit enforced where the money is

A Check costs money — a model call and up to two lookups — and the endpoint is public with no accounts in front of it, so a single loop left running would spend the owner's budget until it ran out and the app stopped working for the people it was built for. The cap is a fixed window of twenty Checks per caller per ten minutes, held in memory: generous for a real person, who checks a handful of messages and not twenty, and tight enough that an accident is noticed before it is expensive. The caller is taken from the first entry of `x-forwarded-for`, because that header lists the original caller first and each proxy after it — keying on the last entry would identify every request as our own edge server and rate-limit the entire world as one caller. A caller who cannot be identified shares a single bucket rather than being waved through, which is the safer way round: the cost of being wrong is a stranger waiting a few minutes, against a bill that cannot be undone.

What this deliberately is not is a security control, and the code says so rather than implying otherwise. On a serverless host each instance keeps its own counts, so the effective ceiling is the limit multiplied by however many instances happen to be warm, and a restart forgets everything. Anyone rotating addresses walks straight past it. Backing it with a database would fix all of that and would be the first thing to break the promise in ADR 0005 that nothing is stored, so it is not done. The limit that genuinely cannot be out-run is the spend cap set at the model provider, because it is enforced where the money is rather than where the request arrives; the deployment wizard sets that before it deploys anything, and the in-memory cap is a brake in front of it rather than a substitute for it.

The message a rate-limited Checker sees is "That is a lot of checks in a short time. Please wait a few minutes and try again." There is a test asserting it contains none of "rate limit", "429", "quota" or "throttled". The person reading it is frightened and not technical, and an error written for a developer would read to them as the app being broken — which, at the moment they most need to trust it, is worse than the wait itself.
