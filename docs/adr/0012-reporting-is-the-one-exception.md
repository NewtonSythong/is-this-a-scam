# Reporting is the only thing kept, it is the Checker's own decision, and it does not accumulate

A scam library is only as useful as it is current, and the people best placed to say what is circulating this week are the people receiving it. So a Checker can report a Message, and a reported Message is stored until somebody has read it. That is a real reversal of ADR 0005, and rather than soften that ADR it is recorded here in full, with the page copy changed to match: the app now says "It is not saved — unless you choose to report it", because a privacy promise that quietly stops being true is worse than one that was never made.

Everything about the design follows from that being a deliberate act rather than a side effect of using the app. Reporting is a separate endpoint from checking, so no Check can store a Message by accident. That endpoint requires an explicit `consent: true` and refuses without it — the requirement lives in the API rather than only in the page, so a client that forgets to ask cannot store somebody's message, and any future client is forced to confront the question. The interface asks twice: the first tap opens a panel that shows the Message back and says plainly that a name, an address or a family member's name in it would be kept too, and only the second tap sends it. Nothing about the reporter goes with it — not their address, not a session, not anything derived from either — so there is nothing about them to leak, and a test asserts the stored record contains no trace of the caller.

Reports do not pile up. Once a report has been turned into a library entry or dismissed it is deleted, and deletion is a first-class part of the store rather than something bolted on later, because keeping a stranger's message after it has served its purpose serves nobody. The review queue itself sits behind a shared secret, and a deployment with no secret configured refuses everything rather than serving the queue openly: an unset token must never mean "no lock", since the failure mode of failing open here is publishing other people's private messages. A wrong token is answered with a 404 rather than a 401, so the queue does not announce that it exists to somebody guessing at addresses.

Reports are kept in a SQLite file, through `node:sqlite`, which is built into Node and so needs no dependency, no account and no connection string. That is durable wherever the filesystem is — a laptop, an ordinary server — and it is not durable on a serverless host, where every instance has its own disk and instances are discarded without warning. A SQLite file there is not storage; it is a cache that looks like storage.

So the app is told which situation it is in rather than left to assume. `reportsFor()` returns the store together with whether it can be trusted to keep what it is given, and where it cannot, the report endpoint refuses with a 503 saying plainly that nothing was kept and that the check itself still worked. That refusal happens before the request body is even read. This is the part worth stating outright, because the first version of this feature got it wrong: accepting somebody's message, thanking them for it, and then losing it is the worst of the available outcomes — they gave up their privacy and nobody was warned. An app that cannot keep a report must decline it and say so.

A hosted database remains the answer for a serverless deployment. When one is chosen it is another branch in `reportsFor()` and another adapter behind `ReportStore`, and nothing above that line changes.
